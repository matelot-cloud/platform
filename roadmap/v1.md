built in this order.** Each milestone lists what it takes from the big roadmap, its acceptance
criteria, and status. Everything not listed here is deferred until v1 ships.

## Milestone details

### M3 — remaining: managed runners ✅ (M12 slice 2)
A `runner` StatefulSet in the cell chart (same agent image), auto-registered into the cell's
"Managed" pool on start; scale by replicas. Acceptance: fresh cell → Security pipeline runs
without the customer installing anything.

### M4 — Product inventory (v1)
* **Releases**: git tags (semver-ish) and GitHub/GitLab releases synced per repository; a release
  belongs to a service; "current version per environment".
* **Container images**: registry connections (GHCR, Docker Hub, GitLab registry, generic v2 with
  token); image inventory with digests and tags; image ↔ service link; image ↔ release by tag.
* **Deployments**: `POST /environments/:id/deployments { release | image digest, version }` from
  CI or the CLI; manual entry in the UI; a Kubernetes inventory job (runner with cluster access
  lists namespaces/workloads/images → deployments). Environments become live.
* Acceptance: after a tag push the release exists; after `security deploy --env production` the
  environment shows the version and image; the Kubernetes job maps a namespace to an environment.

#### CI tokens (pulled forward from M8, done)
Signed machine credentials (`api_tokens`, migration `0008`): created on a project / team /
workspace / organization by whoever manages members there, presets (*deploy*, *pipeline*, *full*),
optional expiry, revocation, last use; secret shown once, stored encrypted. Requests use
`Authorization: SecOps-HMAC-SHA256 keyId,ts,nonce,sig` (HMAC over ts + nonce + method + path +
sha256(body)); ±5 min window, single-use nonces in Redis; the guard runs before the JWT guard;
token principals get exactly their permissions at their scope and appear in the audit trail as
`CI token <name>`. Client: `tools/secops-ci/secops.sh` (bash + openssl + curl) and the composite
GitHub Action `tools/secops-ci`; `docs/ci-integration.md`. Verified: release / deploy / pipeline
through signed requests, replay, tamper and stale-timestamp rejection, out-of-scope 403, revocation.

### M5 — SBOM

created, schedule; normalized components (purl), transitive graph, licenses; history per release;

#### M4 addendum — registries (done)
Three ways images reach the platform, one inventory: (1) **built-in registry** — Docker
Distribution in the cell (`docker compose` service and Helm Deployment/PVC/Ingress) with token auth
delegated to the API (`GET /api/v1/registry/token`, RS256 tokens with libtrust key ids): teams
`docker login <host> -u <CI token key id> -p <secret>`; a project token may push/pull only under
`<project-slug>/…`; pull-only tokens cannot push; anonymous gets nothing; push notifications
(`POST /api/v1/registry/events`, shared secret) register the image on `<project>/<service>`, record
tag + digest and queue an image SBOM; the platform reads its own registry and runners pull from it
with self-issued tokens. (2) **external registry connections** (GHCR, Docker Hub, GitLab, Harbor,
any v2) with robot tokens, tags refreshed every 15 min. (3) **images reported by the deploy step**,
ideally by digest. UI: registry guidance card on the Images tab; CI token preset *registry*.
Verified against a real Distribution 2.8.3 and Syft.

#### Release-centric inventory (done)
Images link to releases by **version** (`1.6.0`/`v1.6.0`) or by **commit** (tag equals the release's
commit sha, `sha-<prefix>` or a ≥7-char prefix) — the way CI tags build images — so a release created
later from a tagged commit picks up the images already built and deployed for it. One joined
endpoint `GET /services/:id/inventory` returns environments (current release, commit, image tag +
digest, SBOM of what runs, since, source), releases (commit, images, environments running it, SBOM)
and images (tags with release and "running in"). Inventory page: *Running now* table per service,
Releases with *Images* / *Runs in*, Container images with *Release* / *Running in*. Verified: sha
build promoted to staging, then the commit tagged → release 5.1.0 shows the image and Staging;
Staging shows release 5.1.0 with commit and digest.

#### Registry reconcile (done)
The worker lists the built-in registry's catalog and tags every 2 minutes with a platform token and
replays them as push events (idempotent): repositories/tags missing from the inventory are
registered and scanned, environment repositories become deployments. Push notifications make it
instant; when they cannot reach the API (proxies, Docker Desktop/WSL networking, restarts) nothing
is lost. Verified: inventory and deployments wiped → rebuilt from the registry within one pass.
CLI: `secops registry login`, `secops registry path --service|--env`; `GET /services/:id/registry`.

#### Registry namespaces and protected environments (done)
Paths are the platform path (`<workspace>/<team>/<project>/<service>[/<environment>]`); a token's
prefix is its scope's path (project/team/workspace; organization = any). Environments can be
**protected** (`environments.settings.protected`): the registry token endpoint drops `push` on that
environment repository unless the CI token lists the environment (`api_tokens.environments`,
migration `0012`); promotion and the deployment API apply the same rule to token principals; UI
users need `deployment:write`. Verified: build token (allowed: staging) → push builds ✓, staging ✓,
prod pull-only, promote/deploy to prod refused (400/403); release token (allowed: prod) → push ✓;
admin promote to protected prod ✓. CI snippet now carries GitHub Actions and GitLab CI templates.

#### Environment repositories in the built-in registry (done)
Team model: `<project>/<service>:<tag>` are **builds** (scanned on every push); each environment has
its own repository `<project>/<service>/<environment-slug>` — **pushing or promoting an image
there is the deployment** (source `registry`, migration `0011`); clusters pull from the
environment repository. *Promote* (UI, `secops promote`, `POST /environments/:id/promote`) copies
a build server-side with blob mounts — no re-upload — and the registry's own push event records the
deployment. One SBOM per digest (builds only). `GET /environments/:id/registry` gives the path and
pull/push commands. Verified against Distribution: build push → promote → Staging 4.8.0; direct CI
push to `…/prod` → Production 4.8.0 superseding the API-recorded 6.0.0; a path that is not an
environment slug is recorded as a build only.

#### CLI package (done, pulled forward from M8)
`apps/cli` → npm **`@secops-platform/cli`** (zero dependencies, Node ≥ 18): `whoami`, `deploy`,
`release`, `pipeline [--ref] [--wait]` (exit 1 when the pipeline does not succeed — usable as a gate
today), `sbom`, `request`; `--json`; exit code 3 on authentication failure. GitHub Action
`tools/setup-cli` installs it and exports the variables; `.github/workflows/publish-cli.yml`
publishes on `cli-v*` tags with npm provenance. The bash script stays for CIs without Node.

#### Builds on every push (done)
GitLab model: **every push is a build that gets scanned; a release is the build with a tag.**
Project setting *Automation → Run the security pipeline on push* (default branch / every push /
off, template selectable; `projects.settings`, migration `0010`). The GitHub push webhook starts
the pipeline on the pushed commit (`trigger: push`, `ref` = commit SHA); the runner checks out the
exact commit (shallow fetch by hash, full fetch fallback). Without the App: `secops.sh pipeline
--service … --ref $GITHUB_SHA` from CI. Every push to the built-in registry already triggers an
image SBOM. Verified: a plain commit → pipeline #5 → checkout @ SHA → SBOM stored for the build,
not linked to a release.

### M6 — Vulnerability correlation
Worker mirrors OSV (purl ranges), NVD (CVSS/CWE), CISA KEV, EPSS; correlation on every new SBOM and
on every intelligence update; findings with states open / in progress / fixed (verified by rescan)
/ accepted / false positive / not affected (VEX). Acceptance: new KEV entry → affected findings
within minutes with product, release, repository, image, environment.

#### M6 progress log
* Slice 1 (done): advisory cache (`advisories`, migration `0016`) fed by **OSV** (`querybatch` per
  component, details per advisory), enriched with **CISA KEV** and **FIRST EPSS**; CVSS v3 base
  score computed from vectors (`osv-mapping.ts`, tested); purl → OSV ecosystem mapping incl.
  Alpine/Debian/Ubuntu/RHEL-family distro packages; `component_checks` re-check every component
  daily so new advisories surface without a new build. **Findings** per service × component ×
  advisory with states open / fixed / accepted / false_positive / not_affected, fixed version derived
  from OSV ranges, links to every SBOM containing the component; auto-**fixed** when the vulnerable
  version is gone from the latest build and from everything deployed (reopens if it comes back);
  accepted findings close too, false positives / not affected keep their verdict. Correlation runs
  right after each SBOM ingest and every 10 minutes in the worker; enrichment refreshes daily.
  API: org/project/service/SBOM finding lists (severity, status, KEV, search, "running somewhere"),
  detail with affected releases/images and environments running them, status change with note
  (audited; `fixed` reserved to the platform), summaries (open by severity, KEV, in production),
  re-correlate. UI: Vulnerabilities pages (org + project) with KPIs, filter chips and finding window;

  `OSV_API_URL`/`KEV_FEED_URL`/`EPSS_API_URL` overrides for tests and air-gapped mirrors).
* Trend: daily `environment_finding_snapshots` (migration `0017`) written after every correlation
  and every 6 h, backfilled 90 days from deployment history × finding timeline on first worker start

* Slice 2 — code scanning (done): runner executes `secrets` and `iac` jobs with **Trivy 0.74**
  (`trivy fs --scanners secret|misconfig`, offline: built-in secret rules, embedded misconfiguration

### Matelot registry as a connection
Migration 0029 adds provider `matelot`. Connections → Container registries → **Matelot registry** (built-in) creates a connection at a workspace, team or project (not the organization: namespaces start at the workspace). No credentials are stored; the connection records the namespace `<workspace>[/<team>[/<project>]]` on the cell's `REGISTRY_HOST` and is connected immediately. Manage shows the image repositories of every service below (`GET /integrations/:id/matelot-repositories`), what the registry does, and the GitHub Actions / GitLab CI / Bitbucket Pipelines jobs (login with the CI token → build/push → pipeline → gate → promote) plus a Kubernetes pull-secret recipe. The card is disabled when the cell has no registry.
